Stu‑Dent
frontend review

A dental teaching-clinic scheduling system. The backend is the stronger half; the frontend handles the happy path well and the failure path barely at all.

Repo edanperetz2/stu-dent Reviewed 31 Jul 2026 Scope Whole project, frontend-weighted Changes made None — review only

This is a strong project. The domain modelling, the conflict engine, and the restraint shown around the AI features are all better than the average student project — in places better than production code I've seen.

Every frontend issue below shares one root cause: the UI was built for the path where everything works. When a request fails, the app doesn't say so — it says you have no data. That single pattern accounts for the two most serious findings, and fixing it is mostly a matter of using a component that already exists in the codebase.

01 What the project is

Worth stating precisely, because the domain is what makes the engineering interesting.

Dental students must perform real treatments on real patients to graduate, supervised by an attending — a senior dentist who mentors and approves procedures. Today that coordination happens over WhatsApp and spreadsheets. Stu-Dent replaces it.

The hard part is that booking one appointment means simultaneously reserving five things — the student, the patient, the attending, a room, and a piece of equipment — any of which can collide with another booking. That constraint drives most of the architecture.

Roles

StudentBook and edit appointments, manage own patients, forum, direct messages, reports
AttendingApprove student requests, view own schedule, leave feedback on students, reports
PatientRequest appointments, message their student, leave feedback, set scheduling preferences
AdminManage users, rooms and equipment; clinic-wide resource calendar; moderate the forum

02 What's genuinely good

Not padding. These are decisions worth keeping, and worth knowing are strong so they don't get "refactored away" later.

The conflict engine is properly built

find_conflicts runs targeted per-resource queries so the app can tell you which of the five resources blocked you — instead of surfacing a generic Postgres constraint error with no way to know which of 5 constraints fired. The DB-level exclusion constraints stay underneath as a genuine race-condition net.

The waitlist design is the best idea in the project

You don't "join a waitlist" from a form. You join it because a real booking attempt failed, and the entry records why. First-come-first-served ordering uses a monotonic sequence column — a correct diagnosis, since created_at ties inside a single transaction.

The AI trust boundary is drawn in the right place

The model never sees the database, never writes a query, and never books anything. It extracts candidate names and a date phrase; every ID and date is then resolved deterministically against real rows and server time. Unsupported questions get "I can't answer that yet" rather than a confident guess.

Medical confidentiality was actually considered

redact_conflicts_for_patient stops a patient from learning that their own student is busy treating someone else — while students, attendings and admins viewing the identical data still see the real cause. That's a real privacy threat model, and most student projects don't have one.

Code hygiene is clean

tsc -b passes with zero errors. oxlint reports 4 warnings, all trivial fast-refresh notes. Every finding below is design- or UX-level, not a correctness bug the tooling should have caught.

The comments explain why

Unusually thorough, and they document reasoning and rejected alternatives rather than restating the code. This is rare and genuinely valuable — it's how I was able to review the project this quickly.

03 Critical findings

Four issues. The first two are really one defect seen from two angles, and fixing them together is the highest-value work available in this codebase. The fourth was found by inspecting the running app, not by reading source.

P0-1

A failed request is displayed as "you have no data"

When a list query fails, the page renders its empty state instead of an error. A student whose session has expired, or who is on a flaky clinic wifi, is told their schedule is empty — while it sits intact on the server.

The codebase already knows about this. components/StateText.tsx exports an ErrorText component whose own docstring says several pages "rendered their empty-state text for a failed request too, indistinguishable from genuinely having no data." That fix reached only 3 of 14 pages. The other 11 still destructure { data, isLoading } and never check isError.

Verified live in a browser with every API call returning 401:

No appointments yet. Click "New Appointment" to create one.
Where · Fixed in: WaitlistPage, FeedbackPage, ReportsPage. Still affected: AppointmentsListPage, PatientsListPage, MessagesPage, NotificationsPage, ForumListPage, ForumPostCard, PreferencesPage, RegisterPage, admin UsersPage / RoomsPage / EquipmentPage, and AppLayout's three badge queries.

Actions

  1. Audit all 14 pages for a useQuery destructure that omits isError.
  2. Adopt one ordering convention everywhere — error → loading → empty → data — and hold it in review.
  3. Give ErrorText a retry affordance, not just red text: a "Try again" button wired to the query's refetch.
  4. Add a shared useListQuery wrapper (or a lint rule) so a new page physically cannot forget the error branch.
  5. Add one test per page asserting a rejected query renders the error state and not the empty state. This is what keeps it fixed.
P0-2

Nothing in the app handles an expired session

JWT_EXPIRE_MINUTES=30, there is no refresh token, and the only logout() call in the entire codebase is the manual button in the header. httpClient.ts never inspects a 401.

So thirty minutes into any session every request starts failing — and because of P0-1, the user sees false empty states with no hint that logging in again would fix it. Thirty minutes is shorter than a clinic shift.

A page reload does recover, because the bootstrap effect clears the bad token and bounces to login. That's exactly why this is easy to miss in testing and unpleasant in real use: the bug only appears if you leave a tab open, which is what real users do all day.

Where · src/api/httpClient.ts (no 401 branch) · src/auth/AuthContext.tsx · .env.example:10

Actions

  1. Handle 401 centrally in httpClient.ts — one place, not per page.
  2. On 401: clear stored auth, redirect to /login, and show an explicit "Your session expired — please log in again". Never fail silently.
  3. Remember the attempted destination and return the user there after re-login.
  4. Decide session length deliberately: raise the expiry, add refresh tokens, or warn before expiry with an extend option. Pick one and write down why — it's a product decision, not a config default.
  5. Stop TanStack Query retrying 401s. It currently retries 3× with backoff, so the user waits several seconds before even the wrong message appears.
P0-3

The WebSocket reconnects forever against a dead token

RealtimeContext reconnects on a fixed 3-second timer with no backoff and no attempt cap. When the token expires the server closes the socket immediately, so the client opens a new one every 3 seconds — indefinitely.

The same happens when the backend is simply down: every open tab hammers it once a second-and-a-half on average, precisely while it's trying to come back up.

Where · src/realtime/RealtimeContext.tsx — RECONNECT_DELAY_MS = 3000, socket.onclose

Actions

  1. Add exponential backoff with jitter and a ceiling around 30 seconds.
  2. Cap consecutive failures, then stop and offer a manual "Reconnect" control.
  3. Treat an auth-failure close code differently from a network drop — an expired token should route into the P0-2 flow, not the retry loop.
  4. Wrap the onmessage JSON.parse in try/catch; one malformed frame currently throws inside the handler.
P0-4

The entire sidebar navigation is unreachable by keyboard

Mantine's <NavLink> renders an <a>, but this code passes it an onClick handler and no to or href. An anchor without an href is not focusable, and no tabIndex is supplied to compensate. All eight items are therefore inert to the keyboard — they respond only to a mouse click.

Measured in the running app, logged in as a student:

totalFocusableOnPage:  28
anyInsideNavbar:        0

tab order → "Toggle navigation" → logo → "Log out" → page content
            (all 8 nav items skipped entirely)

A keyboard-only user can reach the burger, the logo and the logout button, and then lands in the page body. They cannot move between pages at all. This is a WCAG 2.1.1 Keyboard (Level A) failure — the most fundamental accessibility requirement there is.

Two related defects ride along in the same six lines. There is no active state: NavLink's active prop is never passed and useLocation is never called, so no page is ever marked current (aria-current is null on all eight). And because there's no href, Cmd/Ctrl-click can't open a page in a new tab, middle-click does nothing, and there's no "copy link address".

All three vanish with the same fix, which is already demonstrated in the same file — the header logo uses component={Link} correctly. This is an oversight, not a misunderstanding.

Where · src/layouts/AppLayout.tsx:164–186 — compare with the correct component={Link} usage at line 122. Verified · live DOM inspection, seeded stack, student role

Actions

  1. Pass component={Link} and to={link.to} so each item renders a real, focusable anchor. Keep the onClick only for closing the mobile drawer.
  2. Re-test with the keyboard alone: Tab must reach all eight items and Enter must navigate. Treat this as the acceptance criterion, not the code change.
  3. Derive active from the current location and pass it, so the current page is visibly marked.
  4. Make the active style more than colour — weight or a left rule too — so it survives colour-blindness and greyscale printing.
  5. Add aria-current="page" to the active item.
  6. Add a "skip to main content" link while you're in this file; it's the standard companion fix and it's ten minutes.

04 High priority

Worth clearing before the demo. None are large.

P1-1

Users can't tell when live updates have stopped

RealtimeContext tracks isConnected and exports a useRealtime() hook — and nothing in the app consumes either. It is dead code. When the socket drops, the app quietly serves stale data.

This matters more here than in most apps. The entire point of the realtime layer is that an auto-promoted waitlist booking appears without a refresh. If the socket is down, the user is looking at a schedule that may be wrong and has no way to know.

Where · src/realtime/RealtimeContext.tsx:132 — useRealtime has zero call sites

Actions

  1. Surface connection state in the header — visible only when disconnected or reconnecting, so it's silent when healthy.
  2. Offer a manual refresh in the disconnected state.
  3. On reconnect, invalidate the relevant query caches so the user catches up on what they missed.
P1-2

Every list fetches every row, forever

There is no pagination, limit, offset or cursor anywhere in src/api/. AppointmentsListPage fetches the complete appointment list and filters and sorts it client-side — including fetching cancelled appointments purely to discard them. Same for messages, notifications, forum posts and the resource schedule.

Fine with seeded demo data. A clinic with a year of history will feel it.

Actions

  1. Add server-side pagination, starting with appointments, notifications and messages.
  2. Make the appointments query date-range scoped — the calendar already knows which week or month is on screen.
  3. Move status filtering server-side.
  4. Add infinite scroll or explicit paging once the API supports it.
P1-3

Dark mode is declared but not implemented

index.css sets color-scheme: light dark, which tells the browser to paint native controls, scrollbars and form widgets dark when the OS is dark. But MantineProvider is called with no props at all — no theme, no defaultColorScheme — there's no <ColorSchemeScript> in index.html, and no toggle anywhere.

On a dark-mode Mac, Mantine renders everything light while the browser renders native chrome dark. The custom CSS compounds it: hover states are hardcoded to --mantine-color-gray-1, a light-mode value.

Both answers are fine here. The current in-between state is the only bad one.

Where · src/index.css:2 · src/App.tsx · index.html

Actions

  1. Decide whether dark mode is in scope.
  2. If no — delete color-scheme: light dark. One line, done.
  3. If yes — add <ColorSchemeScript>, set defaultColorScheme, add a toggle, and replace the hardcoded gray hovers with scheme-aware tokens.
  4. Either way, replace the 18 hardcoded hex colours in .ts/.tsx with theme tokens — the status and resource palettes in AppointmentsListPage duplicate Mantine values by hand and will drift.
P1-4

No autoComplete on any of the 19 form inputs

Zero occurrences across the codebase. Password managers can't reliably fill the login form, browser autofill doesn't offer saved emails, and mobile keyboards don't optimise. This is the cheapest win in the whole review — an afternoon, immediately noticeable.

Actions

  1. Add autoComplete="email" / "current-password" / "new-password" to login and register.
  2. Add the right values to patient and profile forms (name, tel).
  3. Add type="email" / type="tel" for better mobile keyboards.
  4. Verify by actually saving a credential in a password manager and logging back in.
P1-5

Nothing is announced to screen readers

No aria-live region and no role="alert" anywhere. Every error, success and status change is visual-only. Mantine's <Alert> is never used — errors are plain red <Text>, which is both low visual weight and invisible to assistive tech.

There is real accessibility effort here: keyboard handlers on clickable table rows, aria-label on icon-only buttons, prefers-reduced-motion support. But read alongside P0-4 — where the entire primary navigation is keyboard-unreachable — a pattern emerges: the accessibility work went into individual components, and nothing verified the app as a whole. Rows were made keyboard-operable while the nav that gets you to them was not.

That's the more useful takeaway than any single fix: add one end-to-end keyboard pass to the routine, rather than more per-component attributes.

Actions

  1. Wrap form and page errors in Mantine <Alert> with role="alert".
  2. Add a polite aria-live region for async status changes (saved, cancelled, promoted).
  3. Check that toast notifications are actually announced.
  4. Replace role="button" on <Table.Tr> (5 pages) — it overrides the implicit row role and breaks table semantics. Put a real focusable control in a cell instead.
  5. Do one keyboard-only pass and one screen-reader pass over the booking flow. Booking is the core action; it should be the most accessible thing in the app.
P1-6

AppointmentsListPage is a 901-line component

It holds roughly 15 useState, 6 useQuery, 3 mutations, 3 modals, two view modes (list / calendar) × two lenses (personal / resources) × four roles — rendered through a four-branch nested ternary spanning about 200 lines.

To be fair: the logic is correct and the comments are excellent. The problem is size, not quality. It's simply the file most likely to break under future edits and the hardest to test.

Actions

  1. Extract the list table, the resource table and the calendar into sibling components.
  2. Move the create / interpret / waitlist mutation cluster into a useAppointmentActions hook.
  3. Pull the resource-colour and lens logic (hashResourceColor, combinedResourceOptions, resourceCalendarEvents) into its own module — it's self-contained and unit-testable.
  4. Replace the nested ternary with early returns or a small view-resolver map.
  5. Add tests to each extracted piece as it comes out. Do the split because it enables tests, not for tidiness alone.
P1-7

The calendar opens at midnight, in a clinic that opens at eight

The app only permits bookings between 08:00 and 21:30 — that's what APPOINTMENT_START_TIME_OPTIONS and _END_TIME_OPTIONS generate, and the form offers nothing outside it. But the calendar renders the full 24 hours: the <Calendar> is given no min, no max and no scrollToTime.

So roughly 44% of the grid is dead space that can never contain an appointment — eight empty hours above the clinic day and two and a half below — and every visit to the week or day view lands the user at 00:00, needing a scroll to reach any real content. Spotted immediately on opening the seeded app: a 13:00 booking was below the fold.

react-big-calendar takes min and max props directly. This is a two-line fix that reclaims almost half the screen.

Where · src/pages/appointments/AppointmentsListPage.tsx:774–796 · bounds already defined in src/utils/dates.ts:58–61

Actions

  1. Pass min and max to <Calendar>, derived from the same constants the booking form uses — don't hardcode 8 and 21 a second time, or the two will drift.
  2. Set scrollToTime to the start of the working day so the view opens somewhere useful.
  3. Consider whether clinic hours should be configurable by an admin rather than a constant in utils/dates.ts — the app already has admin-managed rooms and equipment, so hours are the odd one out.

06 How the frontend is built

The code as code — how efficient it is, how much it reuses, and how clean it reads. Separate from whether it behaves correctly, which sections 03–05 cover.

Efficiency is already handled — genuinely

This deserves saying first, because it's the part most student projects get wrong and this one didn't:

  • All ~19 routes are React.lazy() behind <Suspense>, which took the main bundle from 657KB to 355KB and killed Vite's chunk-size warning.
  • AuthContext's context value is memoised, so it doesn't re-render every consumer on unrelated state changes.
  • The heavy appointments page memoises its derived lists (visibleAppointments, both event builders, the resource-colour map) rather than recomputing per render.
  • TanStack Query with a 30-second staleTime, and WebSocket events wired to cache invalidation instead of a second parallel state layer. That's the right instinct.

The remaining efficiency gap is data volume, not rendering — see P1-2. Fetching every appointment ever and filtering client-side will outgrow any amount of memoisation.

Reusability is the real weakness

Seven shared components exist for 6,197 lines. The result is the same three-part pattern written out by hand across fifteen pages:

52useMutation blocks
59notifications.show calls
36invalidateQueries calls
12pages repeating the header block
6copies of one keyboard handler
7shared components total

Nearly every mutation in the app is the identical triad: call the endpoint, then on success invalidate a query key and show a green toast, then on error show a red toast via apiErrorMessage. Written out 52 times.

This is the kind of duplication that isn't a bug today and becomes one later — it's exactly how P0-1 happened. The error-state fix reached three pages and stopped, because there was no single place to make it. Consolidating these isn't tidiness; it's how you stop a fix from reaching only a fifth of the app.

TASK

Extract three shared primitives

Ordered by lines removed per hour spent. None of these change behaviour.

  1. useMutationWithToast — takes the mutation function, the query keys to invalidate, and success/error messages. Absorbs the bulk of 52 blocks and all 59 toast calls.
  2. <PageHeader title actions> — the <Group justify="space-between"><Title order={2}> + buttons block currently retyped on 12 pages. Also the natural home for breadcrumbs later.
  3. <ClickableRow> — one component owning the click handler, the Enter/Space handling, focus styling and ARIA. Replaces 6 hand-copied handlers, and is where the P1-5 role fix lands once instead of five times.

A fourth is worth considering but is a bigger call: RoomsPage and EquipmentPage are 224 and 182 lines of near-parallel CRUD. A shared ResourceAdminPage would collapse them, though they have diverged enough that this needs judgement rather than a mechanical merge.

Scope ~600 lines removed Risk low — no behaviour change Unblocks P0-1, P1-5

Cleanliness

Strong overall. tsc -b is clean, oxlint shows four trivial warnings, naming is consistent, and the comments are the best I've seen in a project this size — they explain rejected alternatives, not just what the line does.

Three small blemishes: 11 inline style={{}} escapes that bypass the design system, the 901-line page from P1-6, and one stale comment contradicting another in the same file. All minor next to what's right.

07 Visual design

The app currently looks like unstyled Mantine — which is a specific look, and not a neutral one. Below is what to change, in the order that buys the most.

The single biggest win: the brand colour is absent from the product

<MantineProvider> is called with no props at all. The primary colour is therefore stock #228be6 — Mantine's factory blue, the same blue on every Mantine demo. Meanwhile the logo, sitting in the top-left of every page, is teal and navy.

So the one piece of visual identity the project has is contradicted by every button in it. Adopting a theme derived from the logo is a single-file change that re-skins the entire app, because every component already reads from the theme.

One caution: check the status colours against contrast requirements once chosen. The current yellow #f59f00 on white fails AA for small text, and it's used for awaiting_confirmation — one of the most common states.

Typography: one size doing three jobs

The base font is 18px (set in index.css), which cascades into Mantine's scale. Measured on the live appointments table, the table header and the table body render at the same 15.75px — headers are distinguished only by weight, in pure black. There is no size, colour, or letter-spacing separation, so the eye has nothing to anchor to when scanning a wide table.

The typeface is the raw system stack. That's a safe default, not a decision.

Dropping the base to 16px and giving table headers a smaller, dimmed, letter-spaced treatment buys back roughly a column of horizontal space and makes the hierarchy legible. The 18px base is the reason the eight-column table feels cramped.

Raw database values are reaching the screen

Status badges render the enum verbatim: awaiting_confirmation, no_show. Mantine's badge uppercases them, so a patient sees AWAITING_CONFIRMATION. appointmentActions.ts maps every status to a colour but nothing maps it to a human label.

Notably, the function to fix this already exists — humanizeFieldName in httpClient.ts does exactly this transformation for validation errors, and was simply never reused here. This is the reusability problem from section 06 showing up as a visual defect.

TASK

Visual work, in order of value

  1. Create a theme file with a primary derived from the logo, a navy ink colour, and named status colours. One file; every component picks it up. Check the chosen status colours for AA contrast — the current yellow fails.
  2. Add a status label map next to the existing STATUS_COLORS, or reuse humanizeFieldName. Never render an enum.
  3. Set a real type scale. Drop the base to 16px; give table headers a small, dimmed, letter-spaced treatment so they stop competing with data.
  4. Cut the appointments table from eight columns to four or five. Drop the viewer's own name, collapse start/end into one time range, group rows by day, and replace "—" with a real absence label.
  5. Replace the 18 hardcoded hex values with theme tokens (also required by P1-3).

08 Experience and interaction

Navigation, the booking flow, modals, icons and motion — judged by driving the real app as a student, not by reading the source.

Icons: the library is installed and 88% unused

@tabler/icons-react is a dependency and appears in 3 files out of roughly 25 — the forum vote buttons, one admin page, and one shared component. The navigation, every button, and every status are text-only.

This matters most in the sidebar, where a student scans eight identical-looking text labels many times a day. Icons plus the active state from P0-4 turn that into a glance instead of a read.

The booking modal is the app's core flow, and its hardest screen

Measured live at a 1440×900 viewport: the modal is 495px wide and 810px tall, contains 18 input elements, and its "Request" button sits below the fold. The primary action of the primary flow is not visible when the dialogue opens.

Three structural problems compound it. The optional AI "describe it in your own words" box occupies the top of the modal, pushing the real form down. There is no grouping — patient, timing, resources and notes read as one flat list of eight fields. And time is entered as four separate controls, with no way to say "30 minutes" — the overwhelmingly common case.

Sixteen modals across the app declare no size at all, so they all inherit the same default width regardless of content.

Motion

What exists is thoughtful: hover transitions on the logo, logout button and nav links, all correctly wrapped in a prefers-reduced-motion block. Someone considered this.

What's missing is motion where it would carry meaning rather than decorate. Route changes snap. Table rows expand instantly with no height transition, so the eye loses its place. Toasts appear and vanish abruptly. And with no skeletons (P2-2), every load is a hard cut from "Loading…" to a full table.

The useful principle: animate things that change position or state, not things that are merely decorative. An expanding row, a promoted waitlist entry, and a newly arrived appointment are all worth 150–200ms. A hover lift is not the priority.

TASK

Experience work, in order of value

  1. Rebuild the booking modal — widen it, group the fields into who / when / where / optional, add duration shortcuts, collapse optional fields, and pin the submit button to a footer. Move the AI box behind a "describe instead" toggle so it stops outranking the form.
  2. Add icons to the sidebar and group the items; ship it together with the P0-4 keyboard and active-state fix, since it's the same six lines.
  3. Give every modal an explicit size — 16 currently inherit the default regardless of content.
  4. Add transitions to row expansion and list insertion (150–200ms), so realtime updates and expanding rows don't teleport.
  5. Replace destructive-action confirm modals with an undo toast where the action is reversible. The ConfirmButton guard is correct for real deletions, but it currently interrupts routine actions too.
  6. Reconsider the "(optional)" labels. Marking the three required fields is quieter than marking the five optional ones.
Scope 1 rebuilt modal + ~5 touched files Risk medium — the booking flow is load-bearing Test re-run the cross-role booking walkthrough after

09 Suggested order

Sequenced by value per hour, not by severity alone.

  1. P0-1 and P0-2 together. They're the same user-facing failure from two angles and share a fix. Biggest improvement available for the least work, and ErrorText already exists.
  2. P0-4 — keyboard-reachable navigation. Realistically a one-line prop change, and it lifts the app over a WCAG Level A bar it currently fails outright. Cheapest severity reduction in the list.
  3. P0-3 — WebSocket backoff. Small, contained, and prevents a self-inflicted load problem on your own backend.
  4. P1-4 — autoComplete. An afternoon. Immediately noticeable to anyone who uses a password manager, which is everyone grading it.
  5. P1-3 — the dark-mode decision. Possibly a one-line deletion. Just don't leave it half-declared.
  6. P1-1 then P1-5. Connection indicator (wiring an existing value), then the accessibility pass.
  7. P1-6 before P1-2. Split the component first — pagination is much easier to land in a page that's already been broken up.
